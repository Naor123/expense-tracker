# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Backend (`backend/`, Python 3.12, venv at `backend/.venv`):
```
backend\.venv\Scripts\activate
pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```
Backend tests (pytest, covers `bank/` only so far): `cd backend && .venv\Scripts\python.exe -m pytest tests/ -v`. No linter configured for the backend.

Mock PSD2 ASPSP (for exercising the bank connector without real bank credentials): `cd backend && uvicorn bank.mock_server:app --port 8010`, then set `PSD2_BASE_URL=http://localhost:8010` in `backend/.env`.

Frontend (`frontend/`, React 19 + Vite):
```
npm install
npm run dev        # http://localhost:5173
npm run build
npm run lint        # eslint .
```
No test suite configured for the frontend.

Both dev servers are normally started in separate visible terminal windows (`Start-Process cmd -ArgumentList "/k ..."`), not as background tasks, and are typically already running during development — check before starting new ones.

## Architecture

Two independent processes, no shared code: `backend/` (FastAPI + raw `sqlite3`) and `frontend/` (React 19 + Vite). The frontend talks to the backend over HTTP using `VITE_API_URL` (`frontend/.env`) as the base URL; backend `DB_PATH` (`backend/.env`, default `expenses.db`) points at the SQLite file.

**Backend** — no ORM, parameterized SQL only, Pydantic v2 for all request/response shapes (`models.py`), errors raised via `HTTPException`. `db.py` owns the schema (`init_db`) and seed data; `main.py` holds every route. Each request opens and closes its own `sqlite3` connection (`get_connection()`) — there's no connection pooling or shared session.

Schema:
- `categories(id, name, color)` — seeded idempotently by name (`INSERT ... WHERE NOT EXISTS`), so re-running `init_db()` is safe even after the table already has rows, and new seed categories can be added later without wiping existing ones.
- `expenses(id, amount, category_id, date, note, recurring_id)` — `date` is stored as `YYYY-MM-DD` text; month filtering everywhere uses `date LIKE 'YYYY-MM-%'`.
- `recurring_bills(id, name, amount, category_id, interval_months, month_parity, start_month, active)` — `interval_months` is 1 (monthly) or 2 (bimonthly); when 2, `month_parity` (`'odd'`/`'even'`) picks which calendar months it applies to (odd = Jan/Mar/May/Jul/Sep/Nov). `SEED_RECURRING_BILLS` only seeds into a genuinely **empty** table (`db.py:init_db`, checked once, not per-name like categories) — deliberately *not* the same pattern as categories. `delete_recurring_bill` disables FK enforcement to delete a bill while leaving its already-generated expenses in place as history; seeding by name-if-missing on every restart used to silently recreate a deleted built-in (new id, same name) and start generating a second, duplicate stream of monthly expenses alongside the orphaned original's. Never go back to per-name reseeding here.
- `recurring_generated(recurring_id, month, expense_id)` — tracks which `(bill, month)` pairs have already produced an expense, so generation is idempotent and a user-deleted generated expense is never silently recreated.
- `delete_expense` (`main.py`) also disables FK enforcement for its one `DELETE` statement — `recurring_generated.expense_id` and `bank_transactions.expense_id` reference `expenses.id`, so without this every delete of a recurring- or bank-generated expense row fails with an uncaught FK constraint error.
- `monthly_salary(month, amount)` — one row per month the user has explicitly set via the UI. `get_salary_for_month(conn, month)` in `db.py` resolves a month's salary by taking the most recent row with `month <= requested month` (carry-forward, so setting it once covers future months until changed again); if there's no row at all yet, it falls back to the `MONTHLY_SALARY` env var.

**Recurring bill generation**: `sync_recurring_bills(conn)` in `db.py` walks every active recurring bill from its `start_month` through the current real calendar month (`months_between` + `bill_applies_to_month`), and inserts an expense for any month not already present in `recurring_generated`. This runs at FastAPI startup and again at the top of `GET /expenses`, `GET /summary`, and `GET /months` — so the generated set is always caught up to "now" on read, with no separate scheduler/cron. It's also called once more right after `POST /recurring-bills` to backfill immediately. Deleting a recurring bill (`DELETE /recurring-bills/{id}`) only removes the definition; past generated expenses and their `recurring_generated` rows are intentionally kept (FK enforcement is turned off for just that one DELETE statement, since those child rows must survive).

Category deletion is blocked (409) if it's the last remaining category or if any expense still references it.

**Email insights**: `POST /insights/send-email?month=YYYY-MM` reuses `compute_summary(conn, month)` (the same helper `GET /summary` calls) plus `get_salary_for_month`, then hands off to `backend/mailer.py`'s `send_summary_email(month, summary, salary)` — stdlib `smtplib`/`email.mime` only, no third-party mail dependency. `mailer.py` raises `MailerConfigError` (missing `SMTP_USER`/`SMTP_APP_PASSWORD`/`RECIPIENT_EMAIL`) or `MailerSendError` (SMTP itself failed); `main.py` maps these to 503/502 respectively. A month with no resolvable salary returns 503 before even trying to send.

**Frontend** — functional components + hooks only, one component per file under `src/components/`, no state library. `App.jsx` is the single source of truth: holds `month`, `categories`, `expenses`, `summary`, `recurringBills`, `salary` state and all the `handle*` mutator functions, passed down as props; components call back up rather than fetching independently. `api.js` is a thin axios wrapper, one exported function per endpoint. Colors are CSS variables in `index.css` (`:root` for light, `[data-theme='dark']` for dark) — components never hardcode hex values except where a category's own stored `color` is applied inline (e.g. color dots, pie slices). Theme is persisted to `localStorage` and applied via `document.documentElement.setAttribute('data-theme', ...)`.

`CategoryManager.jsx` (opened via the header's `Settings` icon) doubles as the general settings modal — it holds both category CRUD and the Net Salary inline editor (`salary`/`onUpdateSalary` props), not just categories despite the filename. The header also has a `Repeat` icon (opens `RecurringBillsManager`) and a `Mail` icon (`handleSendInsightsEmail` — fire-and-forget, feedback shown via a transient banner under the header using the shared `success-banner`/`error-banner` classes).

Note: `expense-list[hidden]` needs an explicit `display: none` override in `index.css` — the `.expense-list { display: flex }` class rule otherwise beats the `[hidden]` attribute's default styling.

**Bank connector (`backend/bank/`)** — imports transactions from Bank Hapoalim instead of manual entry. Two interchangeable providers implement the same `BankProvider` protocol (`bank/base.py`), selected via `BANK_PROVIDER` env var and both normalizing to `NormalizedTxn` (`bank/types.py`):
- `bank/psd2.py` — a Berlin Group AIS client for the Bank of Israel's NextGenPSD2 profile (OAuth SCA approach only — the spec's plain `scaRedirect` link is commented out, so authorization is consent → `scaOAuth` link → OAuth2 Authorization Server Metadata → standard authorization-code redirect → `/bank/callback` → token exchange → Bearer-authenticated AIS calls). **Requires a Capital Markets Authority TPP license for production credentials** — Hapoalim will not issue `client_id`/mTLS certs to an individual for personal use. `bank/mock_server.py` is a standalone FastAPI ASPSP replaying the spec's own examples so the whole flow is testable without real credentials.
- `bank/scraper.py` + `bank/sidecar/` — shells out to the Node `israeli-bank-scrapers` package (`bank/sidecar/scrape.mjs`) to log into Hapoalim's own web banking with real credentials and scrape transactions. Works today with your real account; no licensing needed since it's not a PSD2 TPP integration, but it depends on the bank's website not changing and is subject to Hapoalim's own terms of use.

  **Hapoalim requires an SMS OTP roughly every 30 days from an unrecognized device**, and the published `israeli-bank-scrapers` npm release has no code path for it at all — Hapoalim's own scraper only recognizes three login outcomes (success/invalid-password/change-password), so an OTP challenge falls through as an opaque `UNKNOWN_ERROR`. OTP + device-trust support exists only in an **unmerged fork**: [eshaham/israeli-bank-scrapers#1084](https://github.com/eshaham/israeli-bank-scrapers/pull/1084) (`avivghilai/israeli-bank-scrapers#feat/hapoalim-2fa-device-trust`, pinned at commit `b21fe0bcbe8132ffaaa7fc020e07ba67ea51e54e`), which ships source-only (no prebuilt `lib/`). Run `backend/bank/sidecar/setup-scraper.bat` once to clone, build, and wire it in — it's idempotent and safe to re-run. `backend/bank/sidecar/package.json` points at the built output via `file:.vendor/israeli-bank-scrapers-fork` (both `.vendor/` and `node_modules/` are gitignored inside `sidecar/`).

  Two additional fixes on top of that PR, applied automatically by `setup-scraper.bat` from `backend/bank/sidecar/hapoalim-fixes.patch` right after cloning (`git apply`, checked with `--check` first): (1) `showBrowser: true` is hardcoded in `scrape.mjs` — headless Chrome gets served a blank page by Hapoalim's own anti-automation checks (confirmed: headless failed every time, a visible window succeeded first try), so a real Chrome window pops up on the machine running the backend for every scraper login/sync; (2) `hapoalim.ts`'s success-URL matcher didn't recognize every authenticated landing page — a real login redirected straight to `current-account/transactions` instead of `/homepage`, and `fetchData()` needs `window.bnhpApp`, which only the homepage's bootstrap script sets up. Fixed by adding that URL as a recognized success outcome and having `login()` explicitly navigate to the homepage afterward if it didn't land there directly. If the `avivghilai` fork branch ever moves or gets deleted, the patch file has the full diff needed to reapply the fixes onto whatever replaces it.

  Also worth knowing if this breaks again: `bank/scraper.py`'s subprocess pipes must set `encoding="utf-8"` explicitly — without it, Windows defaults to the system codepage (cp1252), and real transaction data (Hebrew merchant names/memos) crashes decoding after a successful scrape, silently losing the result.

  Because OTP retrieval is a callback the library invokes *mid-scrape*, `bank/scraper.py`'s `ScraperClient` runs the sidecar as a **long-lived subprocess spanning two HTTP requests**, not one-shot request/response: `start_login()` blocks until the sidecar emits either a final result or an `awaitingOtp` line, at which point the paused process is stashed in an in-memory `_sessions` dict keyed by a session id; `POST /bank/connect/otp` later calls `submit_otp()` to write the code to that same process's stdin and read the next line (which may itself be another `awaitingOtp` — the library retries wrong codes up to 3 times before giving up). A successful login's `deviceTrustData` (cookies + localStorage) is saved in `secrets_enc` and replayed on every subsequent `POST /bank/sync`, so routine syncs skip OTP entirely; `sync_login()` (used only by `bank/sync.py`) treats an unexpected OTP prompt during a background sync as a hard failure, since there's no user in the loop to answer it — that surfaces as `last_error` on the connection, directing you to reconnect from the Bank Connections screen.

New tables (`db.py`): `bank_connections` (one row per connected account, `secrets_enc` is a Fernet blob keyed by `BANK_ENC_KEY` holding tokens, scraper credentials, or device-trust data; `company_id` identifies which scraper company this is — see below), `bank_transactions` (staging table, `UNIQUE(connection_id, external_id)` makes re-syncing an overlapping date range a no-op — same idempotency role `recurring_generated` plays for recurring bills; `kind` classifies each row, `settlement` tags when it actually clears — see below), `category_rules` (substring-match merchant→category rules, checked by `bank/rules.py:suggest_category`), `salary_rules` (substring-match counterparty→salary-source patterns, checked by `bank/salary.py:match_salary_rule` — see below). `expenses` gained a `bank_txn_id` column (via the same `PRAGMA table_info` migration guard as `recurring_id`).

**Multiple scraper companies (`bank/companies.py`)**: `SCRAPER_COMPANIES` maps a `company_id` ('hapoalim' | 'max') to its credential field name (Hapoalim's scraper class expects `userCode`, Max's expects `username` — checked against the vendored fork's source) and whether it's a `'bank'` or `'credit_card'` kind. `bank_connections.company_id` is the source of truth threaded through `ScraperClient.start_login`/`sync_login` (passed explicitly, no longer read from a single global `SCRAPER_COMPANY_ID` env var — that setting is now just the fallback default). Adding another company later means one new entry here plus a `SCRAPER_COMPANIES` mirror in `BankConnectModal.jsx` for the label/credential-field text; the actual scrape/sync/store pipeline is already company-agnostic.

**Distinguishing credit card charges from bank transfers (`bank/classify.py`)**: `classify_transaction()` tags every row's `kind` at insert time (`bank/sync.py:store_transactions`). A transaction from a *credit-card* company connection (Max) is always `credit_card_charge` — that's an itemized purchase. A transaction from a *bank* connection (Hapoalim) is `credit_card_payment` if its counterparty/description matches a known card-company name fragment (`CREDIT_CARD_COMPANY_NAME_FRAGMENTS` — Max, Isracard, Visa Cal, Leumi Card, Amex, Mastercard; deliberately not bare `"cal"`, which false-matches words like "local"), otherwise `bank_transfer`. A bank-side `credit_card_payment` is the *same money* as the itemized `credit_card_charge` rows from a connected card — counting both would double it — so `store_transactions` auto-`ignore`s it, but **only if a `status='valid'` connection with a credit-card `company_id` currently exists** (`_has_active_credit_card_connection`); with no card connection, that lump sum is the only record of the spend and stays `pending` like anything else. This only affects newly-synced rows, not ones already sitting in the table — re-classify existing rows by hand (`bank.classify.classify_transaction`) if a card connection gets added after the fact. Sync's default window is the current calendar month to date (`main.py:_month_start()`), not a rolling N days, matching how the rest of the app already thinks in calendar months.

**Sync is explicit, never on-read** — unlike `sync_recurring_bills`, `bank/sync.py:sync_bank_transactions` is only invoked from `POST /bank/sync`. It does real network I/O and BOI's spec caps unattended AIS access at a fixed `frequencyPerDay: 100`, so wiring it into `GET /expenses` like the recurring-bill sync would be both slow and a rate-limit risk.

Imported transactions land in `bank_transactions` with `status='pending'` and require review via `POST /bank/transactions/{id}/approve` (or `/ignore`, or bulk-approve) before becoming a real row in `expenses` — this is deliberate, since the recurring-bill generator already creates expenses for bills like Rent/Arnona/Gym, and auto-inserting the bank's version of those would double-count them. Approving dates the resulting expense by the transaction's `booking_date` (purchase date), **not** `value_date` — this is what makes an August purchase count as August's spending even when the card charge doesn't withdraw until September. `GET /bank/transactions` flags `possible_duplicate` when a pending transaction's amount matches an active recurring bill for that month (reuses `db.py:bill_applies_to_month`).

**Settlement timing (`bank/classify.py:classify_settlement`)**: separate from `kind`, every row also gets a `settlement` of `'immediate'` (clears within days — mostly foreign-currency purchases) or `'delayed'` (rides the card company's ~10th-of-next-month lump sum), purely by comparing the calendar month of `value_date` to `booking_date` — no day-count tuning needed, it falls out of the real data. This is informational only (a badge + a pending-cash-flow total in `ImportReviewModal.jsx`) and never changes which month an expense counts toward. Like `kind`, it's computed at insert time — re-classify existing rows by hand if you need to backfill after adding this column to an older DB. `compute_summary` (`main.py`) also exposes it as `pending_settlement` — the sum of the month's `delayed` `credit_card_charge` rows straight from `bank_transactions`, **regardless of review status** (pending or already-approved) — so `ExpensePieChart.jsx` can show "already left your account" (`total - pending_settlement`) vs "due by the 10th" next to the month's total.

**Salary auto-detection (`bank/salary.py`, `salary_rules` table)**: incoming credits (`amount > 0`) are handled per `kind`: card-side credits (refunds etc.) stay auto-`ignored` as before; an incoming `bank_transfer` matching a `salary_rules` pattern gets `status='salary'` and upserts `monthly_salary` for `booking_date`'s month via `db.py:set_salary_for_month` (shared with the manual `PUT /salary` route) — no confirmation needed on repeat months; an incoming `bank_transfer` matching *no* rule stays `pending` so it shows up in `ImportReviewModal.jsx` with a "Mark as Salary" action instead of the usual category/approve controls (mirrors the existing "remember for X" category-rule UX — no blind heuristics, the user confirms once per employer via `POST /bank/transactions/{id}/mark-salary`).

**Re-verifying an expired scraper connection**: when `sync_login` hits an unexpected OTP prompt, the connection's `status` becomes `'error'`. `POST /bank/connections/{id}/reverify` re-runs login with the connection's *already-stored* credentials (decrypted from `secrets_enc`) rather than asking to retype username/password — if OTP is required it returns `{status:'otp_required', session_id}` the same shape `/bank/connect` does, and `POST /bank/connections/{id}/reverify/otp` finishes it, calling `_update_scraper_connection` (an UPDATE-in-place sibling of `_create_scraper_connection`) so the row's id and any already-approved expenses' `bank_txn_id` links stay intact.

Frontend: `BankConnectModal.jsx` (connections list + connect form; opens a blank popup synchronously on click and only sets its `location.href` after the `await onConnect(...)` resolves, since setting it after the await in one step gets popup-blocked) and `ImportReviewModal.jsx` (pending-transaction review, opened from the header's `Inbox` icon which shows a pending-count badge). A connection row with `status === 'error'` (scraper only) shows a `KeyRound` "Reconnect" button in place of the sync button, driving the reverify endpoints above with the same inline-OTP-form pattern as the initial connect flow. The scraper provider's connect form has an "Institution" sub-select (`BankConnectModal.jsx`'s own small `SCRAPER_COMPANIES` map — display labels and credential-field labels only; keep in sync with `bank/companies.py`, the backend source of truth for actual scraping behavior). `ImportReviewModal.jsx` shows a `kind` badge (Bank Transfer / Card Purchase / Card Payment) per transaction. `ExpenseList.jsx` groups by `bank_txn_id` into a third "Imported from Bank" section alongside Recurring/Other.

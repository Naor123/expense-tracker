# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Backend (`backend/`, Python 3.12, venv at `backend/.venv`):
```
backend\.venv\Scripts\activate
pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```
Backend tests (pytest, covers `bank/` only so far): `cd backend && .venv\Scripts\python.exe -m pytest tests/ -v`. No linter configured for the backend.

Mock PSD2 ASPSP (for exercising the bank connector without real bank credentials): `cd backend && uvicorn bank.mock_server:app --port 8010`, then set `PSD2_BASE_URL=http://localhost:8010` in `backend/.env`.

Frontend (`frontend/`, React 19 + Vite):
```
npm install
npm run dev        # http://localhost:5173
npm run build
npm run lint        # eslint .
```
No test suite configured for the frontend.

Both dev servers are normally started in separate visible terminal windows (`Start-Process cmd -ArgumentList "/k ..."`), not as background tasks, and are typically already running during development — check before starting new ones.

## Architecture

Two independent processes, no shared code: `backend/` (FastAPI + raw `sqlite3`) and `frontend/` (React 19 + Vite). The frontend talks to the backend over HTTP using `VITE_API_URL` (`frontend/.env`) as the base URL; backend `DB_PATH` (`backend/.env`, default `expenses.db`) points at the SQLite file.

**Backend** — no ORM, parameterized SQL only, Pydantic v2 for all request/response shapes (`models.py`), errors raised via `HTTPException`. `db.py` owns the schema (`init_db`) and seed data; `main.py` holds every route. Each request opens and closes its own `sqlite3` connection (`get_connection()`) — there's no connection pooling or shared session.

Schema:
- `categories(id, name, color)` — seeded idempotently by name (`INSERT ... WHERE NOT EXISTS`), so re-running `init_db()` is safe even after the table already has rows, and new seed categories can be added later without wiping existing ones.
- `expenses(id, amount, category_id, date, note, is_rent, bank_txn_id)` — `date` is stored as a real `YYYY-MM-DD` calendar date; **"month" is not that date's calendar month** — see the billing-cycle window below, which every month-scoped query uses instead of `date LIKE 'YYYY-MM-%'`.
- `rent_generated(month, expense_id)` — the only remaining auto-generated expense. There used to be a full user-editable recurring-bills feature (`recurring_bills`/`recurring_generated` tables, a Settings UI); it was removed entirely in favor of everything except Rent coming from the bank/card sync. `db.py:sync_rent` walks `RENT_START_MONTH` through `current_bucket_month()` (not the real calendar month — see below) and inserts a `RENT_AMOUNT` expense (`is_rent=1`, dated the **10th** of that month, not the 1st — see why below) for any month not already in `rent_generated`. Runs at FastAPI startup and at the top of `GET /expenses`/`GET /summary`/`GET /months`.

**The billing-cycle month window (`db.py:bucket_month`/`month_window`/`current_bucket_month`)** — this is the single most load-bearing piece of date logic in the app, confirmed explicitly with the user after real confusion (an Aug-1 transaction was landing in "August's" pie when it should count as July's): **"month M" means the half-open date range `[10th of M, 10th of M+1)`, not the calendar month.** A date's bucket is computed by `bucket_month(d)`: day `>= 10` → stays in that calendar month; day `< 10` → shifts back one month (`bucket_month('2026-08-01') == '2026-07'`, `bucket_month('2026-08-10') == '2026-08'`). `month_window(month)` returns the matching `(start, end)` pair for SQL range queries (`date >= start AND date < end`), replacing every old `date LIKE '{month}-%'`/`substr(date, 1, 7)` check — `compute_summary`, `list_expenses`, `GET /months` (which now buckets each distinct `expenses.date` in Python rather than substring-extracting, since the shift can't be expressed as a substring op), `sync_rent`, and `_month_start()` (the scraper's initial fetch-start date) all go through these two functions. **This applies to every expense uniformly — Rent, imported transactions, the few legacy hand-entered rows — there's no special-casing by source.** `sync_rent` dates its generated row the 10th (not the 1st) specifically so it buckets into the *intended* month instead of shifting back one; if you ever see a Rent (or anything else) row dated the 1st–9th, it's stale data from before this rule existed and needs its `date` corrected by hand to land in the right bucket (this happened once already — the original three Rent rows, dated the 1st, were manually moved to the 10th). `current_bucket_month()` is "today's" bucket, which itself can be surprising: on the 5th of a month, you're still inside the *previous* month's cycle, not the new one.
- `delete_expense` (`main.py`) disables FK enforcement for its one `DELETE` statement — `rent_generated.expense_id` and `bank_transactions.expense_id` reference `expenses.id`, so without this every delete of a rent- or bank-generated expense row fails with an uncaught FK constraint error.
- `monthly_salary(month, amount, source)` — one row per month, written either by auto-detection (`source='auto'`) or by the user via `PUT /salary` (`source='manual'`, which detection will never overwrite — see below). `get_salary_for_month(conn, month)` in `db.py` resolves a month's salary by taking the most recent row with `month <= requested month` (carry-forward, so setting it once covers future months until changed again); if there's no row at all yet, it falls back to the `MONTHLY_SALARY` env var. That carry-forward is why a bad detection is dangerous — it propagates forward silently.

**If you ever see `recurring_bills`/`recurring_generated` mentioned in old context**: that feature is gone. `db.py:init_db` runs a one-time `DROP TABLE IF EXISTS` for both (order matters — `recurring_generated` first, then `expenses`'s old `recurring_id` column via `ALTER TABLE ... DROP COLUMN`, *then* `recurring_bills` itself; dropping `recurring_bills` before clearing the column that still references it fails with a FOREIGN KEY constraint error under `PRAGMA foreign_keys = ON`, since `expenses.recurring_id` was a second FK into that table besides `recurring_generated`).

Category deletion is blocked (409) if it's the last remaining category or if any expense still references it.

**Email insights**: `POST /insights/send-email?month=YYYY-MM` reuses `compute_summary(conn, month)` (the same helper `GET /summary` calls) plus `get_salary_for_month`, then hands off to `backend/mailer.py`'s `send_summary_email(month, summary, salary)` — stdlib `smtplib`/`email.mime` only, no third-party mail dependency. `mailer.py` raises `MailerConfigError` (missing `SMTP_USER`/`SMTP_APP_PASSWORD`/`RECIPIENT_EMAIL`) or `MailerSendError` (SMTP itself failed); `main.py` maps these to 503/502 respectively. A month with no resolvable salary returns 503 before even trying to send.

**Frontend** — functional components + hooks only, one component per file under `src/components/`, no state library. `App.jsx` is the single source of truth: holds `month`, `categories`, `expenses`, `summary`, `recurringBills`, `salary` state and all the `handle*` mutator functions, passed down as props; components call back up rather than fetching independently. `api.js` is a thin axios wrapper, one exported function per endpoint. Colors are CSS variables in `index.css` (`:root` for light, `[data-theme='dark']` for dark) — components never hardcode hex values except where a category's own stored `color` is applied inline (e.g. color dots, pie slices). Theme is persisted to `localStorage` and applied via `document.documentElement.setAttribute('data-theme', ...)`.

`CategoryManager.jsx` (opened via the header's `Settings` icon) doubles as the general settings modal — it holds both category CRUD and the Net Salary inline editor (`salary`/`onUpdateSalary` props), not just categories despite the filename. The header also has a `Mail` icon (`handleSendInsightsEmail` — fire-and-forget, feedback shown via a transient banner under the header using the shared `success-banner`/`error-banner` classes). `ExpenseList.jsx` groups expenses into three collapsible sections: Rent (`e.is_rent`), Imported from Bank (`e.bank_txn_id`), Other (neither).

Note: `expense-list[hidden]` needs an explicit `display: none` override in `index.css` — the `.expense-list { display: flex }` class rule otherwise beats the `[hidden]` attribute's default styling.

**Bank connector (`backend/bank/`)** — imports transactions from Bank Hapoalim instead of manual entry. Two interchangeable providers implement the same `BankProvider` protocol (`bank/base.py`), selected via `BANK_PROVIDER` env var and both normalizing to `NormalizedTxn` (`bank/types.py`):
- `bank/psd2.py` — a Berlin Group AIS client for the Bank of Israel's NextGenPSD2 profile (OAuth SCA approach only — the spec's plain `scaRedirect` link is commented out, so authorization is consent → `scaOAuth` link → OAuth2 Authorization Server Metadata → standard authorization-code redirect → `/bank/callback` → token exchange → Bearer-authenticated AIS calls). **Requires a Capital Markets Authority TPP license for production credentials** — Hapoalim will not issue `client_id`/mTLS certs to an individual for personal use. `bank/mock_server.py` is a standalone FastAPI ASPSP replaying the spec's own examples so the whole flow is testable without real credentials.
- `bank/scraper.py` + `bank/sidecar/` — shells out to the Node `israeli-bank-scrapers` package (`bank/sidecar/scrape.mjs`) to log into Hapoalim's own web banking with real credentials and scrape transactions. Works today with your real account; no licensing needed since it's not a PSD2 TPP integration, but it depends on the bank's website not changing and is subject to Hapoalim's own terms of use.

  **Hapoalim requires an SMS OTP roughly every 30 days from an unrecognized device**, and the published `israeli-bank-scrapers` npm release has no code path for it at all — Hapoalim's own scraper only recognizes three login outcomes (success/invalid-password/change-password), so an OTP challenge falls through as an opaque `UNKNOWN_ERROR`. OTP + device-trust support exists only in an **unmerged fork**: [eshaham/israeli-bank-scrapers#1084](https://github.com/eshaham/israeli-bank-scrapers/pull/1084) (`avivghilai/israeli-bank-scrapers#feat/hapoalim-2fa-device-trust`, pinned at commit `b21fe0bcbe8132ffaaa7fc020e07ba67ea51e54e`), which ships source-only (no prebuilt `lib/`). Run `backend/bank/sidecar/setup-scraper.bat` once to clone, build, and wire it in — it's idempotent and safe to re-run. `backend/bank/sidecar/package.json` points at the built output via `file:.vendor/israeli-bank-scrapers-fork` (both `.vendor/` and `node_modules/` are gitignored inside `sidecar/`).

  Additional fixes on top of that PR, applied automatically by `setup-scraper.bat` from `backend/bank/sidecar/hapoalim-fixes.patch` right after cloning (`git apply`, checked with `--check` first): (1) `showBrowser: true` is hardcoded in `scrape.mjs` — headless Chrome gets served a blank page by Hapoalim's own anti-automation checks (confirmed: headless failed every time, a visible window succeeded first try), so a real Chrome window pops up on the machine running the backend for every scraper login/sync; (2) `hapoalim.ts`'s success-URL matcher didn't recognize every authenticated landing page — a real login redirected straight to `current-account/transactions` instead of `/homepage`, and `fetchData()` needs `window.bnhpApp`, which only the homepage's bootstrap script sets up. Fixed by adding that URL as a recognized success outcome and having `login()` explicitly navigate to the homepage afterward if it didn't land there directly; (3) the **OTP path has its own, separate post-verification success-URL check** (a different code block than the one (2) patches — same underlying deep-page redirect, but the library never applied the fix there) that only recognized `/homepage` variants; a real OTP login landing on `current-account/transactions` timed out waiting for a homepage redirect that was never coming and got misreported as `OTP verification failed` even though the OTP was correct and the session was fully authenticated. Fixed with the same URL addition + homepage-redirect-if-needed, applied to both success paths via a shared point. If the `avivghilai` fork branch ever moves or gets deleted, the patch file has the full diff needed to reapply the fixes onto whatever replaces it.

  `HapoalimScraper.runCurrentDebitDiagnostic()` (also in the patch, a no-op unless `DIAGNOSE_CURRENT_DEBIT=1` is set in the sidecar's environment) navigates to `plastic-cards/current-debit` right after a successful login and dumps every `current-debit`/`plastic`/`card`-matching network response to `bank/sidecar/current-debit-diagnostic.json` — this is how the real API shape below was discovered, and it's a rerunnable tool if Hapoalim changes that page again. Don't commit that JSON file if you regenerate it; it contains real account/card numbers and transaction detail.

  **Hapoalim's own bank-issued card (itemized "current debit")**: distinct from Max, Hapoalim can issue its own card (e.g. a Mastercard) that would otherwise only ever show up on the bank feed as a single bulk `credit_card_payment` line (matched via `CREDIT_CARD_COMPANY_NAME_FRAGMENTS`) — no separate company connector needed to itemize it, since unlike Max it's not a different company/login, it's data living inside the *same* Hapoalim session. Two endpoints, both hit from `hapoalim.ts`'s `fetchCardItemizedCharges()` (called from `fetchAccountData()`'s per-account loop, wrapped in try/catch so a failure here can never break the normal bank-transaction fetch):
  - `GET {apiSiteUrl}/cards/transactions-totals?accountId={accountId}&transactionsType=current&lang=he` — discovery. Returns `cards[]` (filtered to `cardIdentification.nonBankCardInd === false` — a non-bank card here would mean something else is being surfaced and gets skipped, since that's handled by its own connector already), each with `cardBookedBalances.nationalTransactionsTotal[]` / `internationalTransactionsTotal[]` — national ≈ domestic/bulk-on-the-10th (our `delayed`), international ≈ foreign-currency (our `immediate`), the same two-speed split already modeled for Max, just bundled under one connection instead of a separate one. Each entry has its own `debitDate` (`YYYYMMDD`).
  - `GET {apiSiteUrl}/cards/transactions?accountId=...&cardSuffix=...&cardIssuingSPCode=...&cardIdServiceProvider=...&debitDate={YYYYMMDD}&debitEventOrigin={1|2}&cardIdHapoalim=...&lang=he` (`origin=1` national, `=2` international) — itemized detail per `(card, debitDate)`. Returns `transactionsDetails[]`: `currencyAmount.amount`, `eventDate`/`debitDate` (`YYYYMMDD`), `merchantDetails.merchantName`, `transactionRreferance` (upstream typo, real field name, don't "fix" it).

  `fetchCardItemizedCharges()` flattens all of this into `CardItemizedCharge[]` (`externalId` built as `` card-${cardSuffix}-${transactionRreferance}-${debitDate} ``, prefixed so it can never collide with a regular transaction's external id on the same connection), attached to each account as `cardItemizedCharges` (`transactions.ts`'s `TransactionsAccount` type). `scrape.mjs` passes it straight through in the stdout payload, defaulted to `[]`.

  Python side: `bank/scraper.py`'s `_map_card_itemized_transaction()` maps each into a `NormalizedTxn` (`amount` forced negative, `counterparty` = merchant name, `raw=t` so the original `origin` field survives onto `NormalizedTxn.raw["origin"]`); `_handle_response` returns this as a parallel `card_itemized_by_account` dict alongside `transactions_by_account`. `bank/sync.py`'s `_fetch_scraper` returns both. `bank/sync.py:store_card_itemized_transactions` is the shared helper (used by `sync_bank_transactions` and by `main.py`'s `_create_scraper_connection`/`_update_scraper_connection`, the initial-connect equivalent) that splits the itemized batch by `raw["origin"]` and calls `store_transactions` twice — `force_kind="credit_card_charge"` both times (bypassing `classify_transaction()`, which would never tag a `company_id='hapoalim'`-connection row as a card charge otherwise — see `CREDIT_CARD_COMPANY_IDS`), `force_settlement="delayed"` for national and `"immediate"` for international (see the settlement section above). This itemized batch is always stored **before** the regular batch in the same sync — order matters: `_has_itemized_charge_for_debit_date(conn, connection_id, value_date)` is a same-connection auto-ignore check (OR'd alongside the cross-connection `_has_active_credit_card_connection`) that looks for an already-inserted `credit_card_charge` row on the *same* connection with a matching `value_date`, and it only finds anything if the itemized rows landed first in this same sync.

  Verified against a real account: the discovery+detail calls returned real itemized data (49 charges for a pending ~₪3,467 national cycle, plus the already-known WOLT/Apple-etc. shape). The bulk-line auto-ignore itself is timing-dependent and can only be confirmed once an actual bulk "מסטרקרד" charge posts to the regular bank feed on/around the 10th, since Hapoalim's `current-account/transactions` never shows a bulk debit before it's actually charged — the itemized preview data, by contrast, is available well ahead of that.

  `HapoalimScraper.runCurrentDebitDiagnostic()` (in the patch, a no-op unless `DIAGNOSE_CURRENT_DEBIT=1` is set in the sidecar's environment) is what discovered the API shape above — navigates to `plastic-cards/current-debit` right after a successful login and dumps every `current-debit`/`plastic`/`card`-matching network response to `bank/sidecar/current-debit-diagnostic.json`. Kept as a rerunnable tool if Hapoalim changes that page again. Don't commit that JSON file if you regenerate it; it contains real account/card numbers and transaction detail.

  Also worth knowing if this breaks again: `bank/scraper.py`'s subprocess pipes must set `encoding="utf-8"` explicitly — without it, Windows defaults to the system codepage (cp1252), and real transaction data (Hebrew merchant names/memos) crashes decoding after a successful scrape, silently losing the result.

  Because OTP retrieval is a callback the library invokes *mid-scrape*, `bank/scraper.py`'s `ScraperClient` runs the sidecar as a **long-lived subprocess spanning two HTTP requests**, not one-shot request/response: `start_login()` blocks until the sidecar emits either a final result or an `awaitingOtp` line, at which point the paused process is stashed in an in-memory `_sessions` dict keyed by a session id; `POST /bank/connect/otp` later calls `submit_otp()` to write the code to that same process's stdin and read the next line (which may itself be another `awaitingOtp` — the library retries wrong codes up to 3 times before giving up). A successful login's `deviceTrustData` (cookies + localStorage) is saved in `secrets_enc` and replayed on every subsequent `POST /bank/sync`, so routine syncs skip OTP entirely; `sync_login()` (used only by `bank/sync.py`) treats an unexpected OTP prompt during a background sync as a hard failure, since there's no user in the loop to answer it — that surfaces as `last_error` on the connection, directing you to reconnect from the Bank Connections screen.

New tables (`db.py`): `bank_connections` (one row per connected account, `secrets_enc` is a Fernet blob keyed by `BANK_ENC_KEY` holding tokens, scraper credentials, or device-trust data; `company_id` identifies which scraper company this is — see below), `bank_transactions` (staging table, `UNIQUE(connection_id, external_id)` makes re-syncing an overlapping date range a no-op — same idempotency role `rent_generated` plays for the rent generator; `kind` classifies each row, `settlement` tags when it actually clears — see below), `category_rules` (learned merchant→category rules, `UNIQUE` on `pattern`, checked by `bank/rules.py:suggest_category` — see below). `expenses` gained a `bank_txn_id` column via a `PRAGMA table_info` migration guard.

**Multiple scraper companies (`bank/companies.py`)**: `SCRAPER_COMPANIES` maps a `company_id` ('hapoalim' | 'max') to its credential field name (Hapoalim's scraper class expects `userCode`, Max's expects `username` — checked against the vendored fork's source) and whether it's a `'bank'` or `'credit_card'` kind. `bank_connections.company_id` is the source of truth threaded through `ScraperClient.start_login`/`sync_login` (passed explicitly, no longer read from a single global `SCRAPER_COMPANY_ID` env var — that setting is now just the fallback default). Adding another company later means one new entry here plus a `SCRAPER_COMPANIES` mirror in `BankConnectModal.jsx` for the label/credential-field text; the actual scrape/sync/store pipeline is already company-agnostic.

**Distinguishing credit card charges from bank transfers (`bank/classify.py`)**: `classify_transaction()` tags every row's `kind` at insert time (`bank/sync.py:store_transactions`, unless overridden — see `force_kind` below). A transaction from a *credit-card* company connection (Max) is always `credit_card_charge` — that's an itemized purchase. A transaction from a *bank* connection (Hapoalim) is `credit_card_payment` if its counterparty/description matches a known card-company name fragment (`CREDIT_CARD_COMPANY_NAME_FRAGMENTS` — Max, Isracard, Visa Cal, Leumi Card, Amex, Mastercard; deliberately not bare `"cal"`, which false-matches words like "local"), otherwise `bank_transfer`. A bank-side `credit_card_payment` is the *same money* as the itemized `credit_card_charge` rows from a connected card — counting both would double it — so `materialize_expenses` ignores it as `card_lump_sum` if **either** a `status='valid'` connection with a credit-card `company_id` exists (`_has_active_credit_card_connection`, the Max case) **or** an itemized `credit_card_charge` already sits on the *same* connection with a matching `value_date` (`_has_itemized_charge_for_debit_date`, the Hapoalim-own-card case — see below); with neither, that lump sum is the only record of the spend and gets imported like anything else. Note `classify_transaction` only returns `credit_card_payment` when `settlement == 'delayed'` — a same-day match on a card-network name is an individual foreign-currency purchase that merely happens to be labelled with the network, not the monthly bulk line, and treating it as one would wrongly ignore a real expense. `kind` is only assigned to newly-synced rows, not ones already sitting in the table — re-classify existing rows by hand (`bank.classify.classify_transaction`) if a card connection gets added after the fact.

**Sync is explicit, never on-read, and scoped to one billing-cycle month** — unlike `sync_rent`, `bank/sync.py:sync_bank_transactions` is only invoked from `POST /bank/sync?connection_id=&month=`. It does real network I/O and BOI's spec caps unattended AIS access at a fixed `frequencyPerDay: 100`, so wiring it into `GET /expenses` like the rent sync would be both slow and a rate-limit risk. The route takes a `month` (billing-cycle, per `bucket_month`/`month_window` above — not `date_from`/`date_to` directly anymore), computes the fetch-start date from `month_window(month)[0]`, and — since the scraper only accepts a start date and always fetches through "now" regardless of an end date (`bank/sidecar/scrape.mjs`), so a fetch starting in July inevitably drags in August's data too — **discards** anything `store_transactions`/`store_card_itemized_transactions` sees whose own `bucket_month(booking_date)` doesn't match the requested `month` (the `target_month` param). Re-syncing a later month picks up whatever got discarded. `main.py`'s `_month_start()` (used only for the *first* connect/reverify, which has no target month and imports everything unfiltered) similarly returns the current bucket's window-start, not the 1st of the real calendar month. The frontend just passes its `MonthPicker`-selected `month` straight through (`BankConnectModal.jsx`'s `handleSync`, prop-drilled from `App.jsx`) — no client-side date math anymore, the backend owns the whole window computation.

**Import is fully automatic — there is no approval queue.** Sync happens in two phases, and the split is load-bearing. `store_transactions` is a *pure staging writer*: it classifies `kind`/`settlement` and inserts every row as `status='new'`, deciding nothing about money. Then `bank/importer.py:materialize_expenses(conn, month)` runs as a separate pass over already-stored rows and decides what becomes an expense. Keeping these apart is not cosmetic:

- `INSERT OR IGNORE` no-ops on rows that already exist, so creating expenses inline would only ever work on a row's *first* sight — anything that failed once, or was staged before this feature existed, could never be imported. A pass keyed on `status` is retryable by construction and idempotent (re-running imports nothing new).
- The bulk-lump-sum guard needs itemized rows to already be in the table. Inline, that made insert *ordering* decide whether a four-figure charge got double-counted. Deferred, ordering is irrelevant — see `test_bulk_card_payment_ignored_even_when_staged_before_its_itemized_rows`.
- Duplicate pairs can arrive in different sync runs; only a post-hoc pass sees both.

Statuses are `new` → `imported` (an expense exists, `expense_id` set) / `ignored` (with an `ignore_reason`) / `salary`. The expense is dated by the transaction's `booking_date` unchanged — bucketing stays a read-time concern via `bucket_month`, never baked into the stored date.

Three ignore gates, in order, each guarding a double-count that is **live in the real data**: `card_lump_sum` (the bulk card debit, when itemized rows for it exist); `rent_duplicate` (amount equals `RENT_AMOUNT` and `rent_generated` already produced that month's row — the bank's own standing-order line would otherwise land on top of the generated one); `itemized_duplicate` (`importer.py:has_itemized_twin`). That last one deliberately does **not** filter on `connection_id`, unlike the cross-connection check it replaced: Hapoalim's own card itemization lives on the *same* connection as its bank feed, so a cross-connection-only test missed that pair entirely. The `settlement='immediate'` constraint on the card side is what keeps it from firing on two same-priced domestic purchases in the same week. The match is symmetric, so the tie-break matters — **keep the `credit_card_charge`** (it carries the real merchant name, e.g. `AMAZON PRIME`) **and ignore the `bank_transfer` twin** (which only carries the card network, e.g. `מסטרקרד`); ignoring "whichever row is flagged" would drop both and lose the expense.

`POST /bank/backfill?month=` runs the same pass over rows already staged but never materialized. It is user-triggered on purpose and never runs at startup — materializing a backlog unannounced is exactly the failure mode to avoid on real financial data.

Deleting an imported expense sets its transaction to `ignored`/`user_deleted` — **terminal on purpose**. Anything non-terminal would just be re-imported by the next materialize pass, silently resurrecting what the user deleted. `POST /bank/transactions/{id}/restore` is the inverse and bypasses every gate, since overriding them is its whole point.

**Auto-categorization (`bank/rules.py:suggest_category`)** runs in the materialize pass, in three layers: learned `category_rules` → the shipped `bank/seed_keywords.py` table (~150 Hebrew/English merchant patterns → category name, resolved case-insensitively and skipped silently if the category doesn't exist — it never auto-creates one) → `Uncategorized`. Learned rules always win, so a user correction beats a shipped keyword forever. Two non-obvious pieces:

- **Everything is normalized through `db.py:normalize_pattern`** (lowercase + collapse whitespace runs) on both sides of the match. Real counterparties arrive as `'סופר  אל הים'` and `'APPLE.COM/BILL         CORK          IE'`; without this a perfectly correct pattern silently never matches.
- **Rules are ordered `LENGTH(pattern) DESC, id ASC`, and `pattern` is `UNIQUE`.** Both exist to fix the same trap: matching returns the *first* hit, so under the old insertion order a correction was silently inert whenever an older, broader rule already matched — the user recategorizes a merchant, the next sync puts it back, and nothing errors anywhere. `PATCH /expenses/{id}` upserts (`ON CONFLICT(pattern) DO UPDATE`) for the exact-match case, and longest-first handles overlapping substrings (`"סופר פארם"` beats `"סופר"`). `init_db` normalizes and de-dupes existing patterns *before* creating the unique index, or the index creation itself would fail and take startup down.

Seed keywords deliberately exclude anything under 3 chars and bare `"מקס"` (it collides with the card-company name fragments and would file the Max lump sum as Shopping). On the real ledger this categorizes ~85% of imported rows; the rest land in `Uncategorized` and get trained away one correction at a time.

**Settlement timing (`bank/classify.py:classify_settlement`)**: separate from `kind`, every row also gets a `settlement` of `'immediate'` (clears within days — mostly foreign-currency purchases) or `'delayed'` (rides the card company's ~10th-of-next-month lump sum). The generic version compares the calendar month of `value_date` to `booking_date` (no day-count tuning, falls out of the real data) and is used for Max and plain bank transfers, where we have no better signal. **Hapoalim's own itemized card charges override this entirely** via `store_transactions`' `force_settlement` param, driven by `store_card_itemized_transactions` splitting on the known `origin` (national=1 always `'delayed'`, international=2 always `'immediate'` — see below) rather than guessing from dates, since the date-comparison heuristic misclassifies a national (bulk-cycle) charge as `'immediate'` whenever its purchase and debit dates happen to fall in the same calendar month (e.g. bought the 1st, debited the 10th). Settlement is informational only (a badge + a pending-cash-flow total in `ImportActivityModal.jsx`) and never changes which month an expense counts toward. `compute_summary` (`main.py`) also exposes it as `pending_settlement` — the sum of the month's `delayed` `credit_card_charge` rows straight from `bank_transactions` within that month's `month_window`, **regardless of status** — so `ExpensePieChart.jsx` can show "already left your account" (`total - pending_settlement`) vs "due by the 10th" next to the month's total.

**`force_kind`/`force_settlement`/`target_month` on `store_transactions`** (`bank/sync.py`): three independent overrides layered onto the same insert loop. `force_kind` bypasses `classify_transaction()` entirely (used for itemized card charges, which would never naturally classify as `credit_card_charge` coming from a `company_id='hapoalim'` bank-kind connection). `force_settlement` bypasses `classify_settlement()` the same way (used for Hapoalim's own card, per above). `target_month`, when given, silently drops (never inserts) any txn whose `bucket_month(booking_date)` doesn't match — this is what makes month-scoped sync actually scoped, per above. `store_card_itemized_transactions` is the shared helper (used by both `sync_bank_transactions` and the initial-connect flow in `main.py`) that reads each txn's `origin` off `NormalizedTxn.raw` and splits into two `store_transactions` calls accordingly.

**Itemized duplicate detection (`bank/importer.py:has_itemized_twin`)**: the bulk-lump-sum dedup above only catches the *monthly total* card payment. A second shape exists: an individual **immediate**-settling card charge (foreign currency, clears in days) can also appear as its own line on the bank feed, unbundled — so the name-fragment match never sees it. The check looks for a same-amount `credit_card_charge` with `settlement='immediate'` whose `value_date` is within 3 days of this `bank_transfer`'s `booking_date`.

Two corrections to the earlier read-time version, both learned from the real ledger: it **no longer requires a different `connection_id`** (Hapoalim's own card itemization lives on the *same* connection as its bank feed, so the cross-connection framing missed that pair outright), and it is now an **auto-ignore at materialize time** rather than a soft read-time flag, since there's no review step left to resolve it in. Verified against the live data: the widened query returns exactly the 2 true pairs and no false positives — the `immediate` constraint is what excludes a same-priced *delayed* domestic purchase in the same week, which is a genuinely different transaction. Because the match is symmetric, the tie-break is essential; see the import section above.

**Salary auto-detection (`bank/salary.py:recompute_salary_for_month`)**: the **largest incoming `bank_transfer` in the month is the salary**, full stop — no patterns, no confirmation. (The old `salary_rules` table is dropped; its only writer was the deleted mark-salary route.) Every other credit is `ignored` as `incoming_credit`, or `card_refund` when it came from the card side. Three details that each exist for a reason:

- It's **re-entrant**: a bigger credit arriving later in the month demotes the previous winner and re-points `monthly_salary`, so running it after every sync converges instead of accumulating stale `salary` rows.
- **`SALARY_MIN` (env, default 3000)** is a floor. Without it, a month whose only credit is a ₪50 refund sets salary=50 — and because `get_salary_for_month` carries forward (`month <= ?`), that ₪50 would propagate into every later month and into the insights email.
- **`monthly_salary.source`** (`'auto'`/`'manual'`) is what stops detection from clobbering a figure the user typed. The auto path's upsert carries `WHERE monthly_salary.source = 'auto'`, making it a single statement rather than a read-then-write. The column defaults to `'manual'` precisely so pre-existing rows are treated as user-set. `DELETE /salary?month=` drops the override and hands the month back to detection.

Salary is keyed by the pass's billing-cycle `month`, not `booking_date[:7]` — this used to be the one place in the app using a raw calendar month.

**Re-verifying an expired scraper connection**: when `sync_login` hits an unexpected OTP prompt, the connection's `status` becomes `'error'`. `POST /bank/connections/{id}/reverify` re-runs login with the connection's *already-stored* credentials (decrypted from `secrets_enc`) rather than asking to retype username/password — if OTP is required it returns `{status:'otp_required', session_id}` the same shape `/bank/connect` does, and `POST /bank/connections/{id}/reverify/otp` finishes it, calling `_update_scraper_connection` (an UPDATE-in-place sibling of `_create_scraper_connection`) so the row's id and any already-imported expenses' `bank_txn_id` links stay intact.

Frontend: `BankConnectModal.jsx` (connections list + connect form; opens a blank popup synchronously on click and only sets its `location.href` after the `await onConnect(...)` resolves, since setting it after the await in one step gets popup-blocked) and `ImportActivityModal.jsx` — a **read-only** log of what the last sync did (salary detected / imported / ignored-with-reason, plus a "Restore as expense" action per ignored row), opened from the header's `Inbox` icon. That badge counts this month's expenses still in `Uncategorized`, which is the only thing left that wants attention now that nothing needs approving. A connection row with `status === 'error'` (scraper only) shows a `KeyRound` "Reconnect" button in place of the sync button, driving the reverify endpoints above with the same inline-OTP-form pattern as the initial connect flow. The scraper provider's connect form has an "Institution" sub-select (`BankConnectModal.jsx`'s own small `SCRAPER_COMPANIES` map — display labels and credential-field labels only; keep in sync with `bank/companies.py`, the backend source of truth for actual scraping behavior).

`ExpenseList.jsx` groups by `bank_txn_id` into "Rent" / "Imported from Bank" / "Other Expenses". **"Other Expenses" is now permanently empty for new data** — manual entry is gone — but the branch is kept and rendered conditionally because a couple of legacy hand-entered rows still exist and still count toward the pie total; deleting the branch would make them invisible but not weightless. Each row's category is an inline `<select>`; changing it calls `PATCH /expenses/{id}` which also upserts a `category_rules` entry. That is the entire feedback loop that replaced the approval queue: correct a merchant once, every future sync gets it right. `handleSyncBank` must `await loadMonthData()` — a sync now creates expenses directly, so the list and pie go stale without it.
